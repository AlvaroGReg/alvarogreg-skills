---
description: Review and update project models with confirmation
---

Review the current project's OpenCode model assignments and propose conservative updates. Respond in Spanish. Do not modify any files until the user explicitly confirms the specific changes.

1. Inspect repository instructions and locate OpenCode configurations applicable to the project: `opencode.json` and `opencode.jsonc`, including those in `.opencode/` and applicable ancestor directories. Also inspect agent and subagent definitions in files and model assignments in commands or other project configuration. Include inherited assignments or effective defaults when identifiable, indicating their origin. Do not reveal secrets. Distinguish project files from global or external configuration: the latter may be inspected to identify effective values but must not be modified without explicit authorization for those files.
2. Query the OpenCode model catalog at runtime using the available model-listing tool or, if unavailable, the official OpenCode interface. Look up models from the provider of each assignment; do not rely solely on prior knowledge or assume a model exists or is available. If the catalog is inaccessible or incomplete for an assignment, say so and do not propose a replacement for it.
3. Compare available identifiers and metadata. Propose only an unequivocally newer version from the same family and provider, preserving the variant, including standard, fast, and ultrafast distinctions and any `#variant` suffix. Similar names alone do not establish succession. If succession, version ordering, availability, or variant equivalence cannot be established with confidence, mark the assignment as uncertain without an automatic replacement. Do not change family or provider. Indicate when an assignment is already up to date.
4. Show a table containing each assignment found, its origin and affected file, the current and proposed models, and the status or reason. Identify inherited values, shared files, and any external configuration; flag assignments without a proposal. If there are no safe changes, report the result and finish without modifying files.
5. Request explicit confirmation of the specific rows or changes the user approves. Stop and wait for their response; do not interpret invoking the command or silence as approval. If approval is ambiguous, ask again. Apply only approved changes and only to authorized files, preserving formatting and unrelated settings. Before editing, verify that the values still match those reviewed; if they have changed, present the affected proposal again and request renewed approval.
6. Verify the resulting configuration with available validation tools and check that the selected models and variants appear in the catalog consulted. Review the diff to confirm it contains only approved changes. Report the changes and checks performed or unavailable, without claiming validation that could not be performed.
